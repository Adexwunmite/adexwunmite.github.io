SQL Server · Data Cleaning

Cleaning a workforce dataset

Tools SQL Server, Azure Data Studio
Duration ~2 weeks
Outcome 100% clean dataset ready for analysis

A raw employee/worker dataset arrived with duplicate records, inconsistent date formatting, missing values, and text fields that weren't standardized. Before any meaningful analysis could happen, I had to get the data into a reliable state. This project shows the SQL approach I use to clean messy operational data.

The Problem

The raw dataset had several common data quality issues:

  • Duplicate employee records (same person appeared 2–3 times with slight variations)
  • Inconsistent date formatting (mix of MM/DD/YYYY and DD-MM-YYYY in the same column)
  • Null values in critical fields (missing hire dates, department names)
  • Whitespace inconsistencies in text fields ("IT Department" vs " IT Department " vs "it department")
  • No standard ID scheme to reliably identify unique employees

This meant any downstream reporting or analysis would be unreliable — dashboards would show inflated counts, trends would be wrong, and any business decision based on this data would be built on a shaky foundation.

My Approach

I built a SQL pipeline that identified and fixed each issue in stages:

  • De-duplication: Identified duplicates using ROW_NUMBER() partitioned by employee name and hire date, kept the most complete record
  • Date standardization: Converted all dates to ISO 8601 format (YYYY-MM-DD) and flagged unparseable values for manual review
  • Text standardization: Used TRIM(), UPPER(), and pattern matching to normalize department names and titles
  • Null handling: Filled forward nulls where appropriate (last known department), flagged impossible nulls (hire date) for escalation
  • Validation: Built a final QA query to check record counts, verify no duplicates remain, and confirm no nulls in critical fields

The SQL

Here's the core de-duplication and cleaning logic:

Step 1: Identify duplicates
WITH ranked_employees AS ( SELECT employee_id, name, hire_date, department, ROW_NUMBER() OVER ( PARTITION BY name, hire_date ORDER BY CASE WHEN department IS NOT NULL THEN 1 ELSE 2 END ) AS rn FROM raw_employees ) SELECT * FROM ranked_employees WHERE rn = 1;
Step 2: Clean and standardize text
SELECT employee_id, UPPER(TRIM(name)) AS name_clean, CASE WHEN department LIKE '%IT%' THEN 'Information Technology' WHEN department LIKE '%HR%' THEN 'Human Resources' ELSE UPPER(TRIM(department)) END AS department_clean, hire_date FROM deduplicated_employees;
Step 3: Standardize dates and handle nulls
SELECT employee_id, name_clean, department_clean, TRY_CONVERT(DATE, hire_date, 23) AS hire_date_clean, CASE WHEN TRY_CONVERT(DATE, hire_date, 23) IS NULL THEN 'REVIEW_REQUIRED' ELSE 'VALID' END AS data_quality_flag FROM text_cleaned_employees WHERE name_clean IS NOT NULL;
Step 4: Final QA check
SELECT COUNT(*) AS total_records, COUNT(DISTINCT employee_id) AS unique_ids, SUM(CASE WHEN data_quality_flag = 'REVIEW_REQUIRED' THEN 1 ELSE 0 END) AS flagged_records, SUM(CASE WHEN name_clean IS NULL THEN 1 ELSE 0 END) AS null_names FROM employees_final;

What I Learned

This project reinforced that data cleaning is not a one-off step — it's a continuous process. Even after this cleanup, new data coming in needs the same treatment. The SQL patterns I built here (ROW_NUMBER partitioning, TRY_CONVERT for safe casting, CASE logic for mapping) became reusable templates for cleaning other datasets that followed.

I also learned to always include a validation step. The final QA query caught an edge case where some hire dates still couldn't parse — flagging these for manual review rather than silently dropping them meant we could handle them appropriately instead of losing data.
